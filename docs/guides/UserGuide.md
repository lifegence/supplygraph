# 利用者ガイド

SupplyGraph の MVP の使い方を説明します。SBOM を取り込み、部品を名寄せし、脆弱性と照合して、影響を受けるリリースと実機を特定するまでが対象です。

画面の項目名は、日本語表示の名前で書きます。英語で表示している場合は、カッコ内の名前を探してください。

## できること、まだできないこと

| 機能 | MVP |
| --- | --- |
| SBOM の取込（CycloneDX JSON、SPDX JSON、SPDX tag-value） | できる |
| 部品の名寄せ | できる |
| OSV との同期と、PURL による照合 | できる |
| 影響を受けるリリースと実機の特定 | できる |
| 実機と現在の構成の CSV 取込 | できる（[手順](ProductUnitImport.md)） |
| SBOM の出力（CycloneDX 1.6、SPDX 2.3 の JSON） | できる |
| NVD との同期、CPE による照合 | Phase 2 |
| 更新キャンペーン、当局への報告、AI の下書き | Phase 2 |

SBOM を出力するには、BOM文書の画面で右上の「SBOM を出力」から CycloneDX か SPDX を選びます。ファイルがダウンロードされます。

- 出力の前に検証が動きます。Error があると内容が表示され、「このまま出力」を押したときだけ出力します。
- 形式に書けない値（URL ではないダウンロード先など）は出力から外し、「警告つきで出力しました」に一覧を表示します。
- 取消済みの文書には、このボタンが出ません。

API で呼ぶ場合は `POST /api/method/supplygraph.sg_bom.export.export_bom` です。`bom_document` に文書名、`format` に `CycloneDX` か `SPDX` を渡すと、応答の `message.content` に出力が入ります。

## 画面を日本語にする

ユーザー（User）の一覧で自分を開き、Language を「日本語」にして保存します。

Frappe 本体には日本語訳がないので、共通の部分（「Search」「Last synced」など）は英語のままです。グラフの凡例（Open、Critical など）も英語で出ます。

## ロール

| ロール | できること |
| --- | --- |
| SG Administrator | すべて。部品の統合（削除を伴う）と設定の変更もここに含まれる |
| SG Configuration Manager | SBOM の取込と受入、リリースと実機の登録、部品の重複検出 |
| SG Security Analyst | 照合結果の変更（誤検知の処理）、影響評価の作成、部品の重複検出 |
| SG PSIRT Manager | 照合結果の変更、影響評価の作成と提出 |
| SG Release Manager | 実機の更新。そのほかは閲覧 |
| SG Compliance Officer | 閲覧（当局への報告は Phase 2） |
| SG Viewer | 閲覧 |
| SG Supplier | Desk には入れない |

## 全体の流れ

1. マスタを登録する
2. SBOM を取り込み、リリースに結び付けて受け入れる
3. 部品を名寄せする
4. 脆弱性を同期する
5. 影響を調べ、実機まで特定する
6. 判定を記録する

## 1. マスタを登録する

次の順に登録します。後のものが前のものを参照します。

| 順 | マスタ | 内容 |
| --- | --- | --- |
| 1 | 製品カテゴリ（Product Category） | 車両、ロボットなど。シリアル番号の形式を正規表現で決められる |
| 2 | ユニットの種類（Unit Type） | ECU などの部品番号 |
| 3 | リリース（Release） | ユニットのソフトウェアの版 |
| 4 | 製品モデル（Product Model） | 車種など。搭載ユニットの構成を持つ |
| 5 | 実機（Product Unit） | 1台ごとの情報と、今載っているリリース |

実機は [CSV でまとめて登録](ProductUnitImport.md)できます。

## 2. SBOM を取り込む

1. SBOM の一覧で「SBOMを取り込む」（Import SBOM）を押し、ファイルを選びます。拡張子は `.json` か `.spdx` です。
2. 取込はバックグラウンドで動きます。終わると画面の右下に結果が出て、一覧に文書が増えます。
3. 文書を開き、状況が「検証済み」（Validated）になっていることを確かめます。
4. **「対象リリース」（Subject Release）を選んで保存します。** 取込の画面ではリリースを指定できません。
5. 右上の「アクション」（Actions）から「受け入れる」（Accept）を選びます。

対象リリースを選ばずに受け入れると、そのリリースの部品として登録されず、影響の調査に出ません。この場合は確認のメッセージが出ます。受け入れると文書は変更できなくなるので、受け入れる前に確かめてください。受け入れた時点でリリースに主 BOM（Primary BOM）がなければ、この文書が主 BOM になります。

検証ルールを満たさない文書は「却下」（Rejected）になり、受け入れられません。文書の検証結果（Validation Results）で理由を確かめ、SBOM を直して取り込み直します。同じ内容のファイルをもう一度取り込むことはできません。

## 3. 部品を名寄せする

同じ部品が別の名前で入ることがあります（`zlib` と `ZLIB` など）。

1. 部品の一覧で、確認の状況が「要確認」（Needs Review）の行に絞ります。SBOM の取込で候補に印が付きます。すでにある部品を調べ直すときは、「アクション」の「重複を探す」（Find Duplicates）を使います。
2. 統合する行にチェックを入れ、「アクション」の「部品を統合」（Merge Components）を押します。
3. 残す部品を選びます。もう一方の名前は別名として残り、次の取込からは残した部品に統合されます。

統合は元に戻せません。「部品を統合」は SG Administrator にだけ表示されます。

## 4. 脆弱性を同期する

SupplyGraph の設定（SG Settings）で「OSVを有効にする」（OSV Enabled）にチェックを入れ、同期の間隔（毎時または毎日）を選びます。カタログにある部品の版のうち PURL を持つものを、OSV に問い合わせます。

すぐに同期するときは、脆弱性の一覧で「OSV と同期」（Sync with OSV）を押します。同期はバックグラウンドで動き、終わると画面の右下に、増えた脆弱性と照合結果の数が出ます。

- ボタンは、脆弱性を変更できるロール（SG Administrator、SG Security Analyst、SG PSIRT Manager）にだけ出ます。
- 同期が動いている間にもう一度押しても、2つ目の同期は始まりません。定期の同期とも重なりません。
- 同期には worker が必要です。

同期すると、脆弱性（Vulnerabilities）と照合結果（Matches）が増えます。PURL を持たない部品、PURL に版が無い部品、版が `^1.0.0` のような範囲になっている部品は照合されません。範囲の部品は、取込の検証結果に `IMP-VERSION-RANGE` の警告が出ます。

## 5. 影響を調べる

1. 「脆弱性の影響」（Vulnerability Impact）を開き、脆弱性を指定します。
2. 影響を受けるリリース、製品モデル、台数が出ます。未搭載のリリースは台数0で出ます。
3. 行の左端にチェックを入れて「実機を表示」（Show Units）を押すと、シリアル番号（自動車なら VIN）の一覧が出ます。選べる行は1つだけです。

「影響なしと修正済みも含める」（Include Not Affected and Fixed）にチェックを入れると、判定で除いたリリースも出ます。

### 開発用の部品

画面を作る道具やテストの部品など、開発だけで使う部品の照合は、外さずに分けて表示します。

- SBOM で開発用とされた部品は、取り込むと開発用になります。CycloneDX では scope が `excluded` の部品、SPDX では `DEV_DEPENDENCY_OF`、`BUILD_DEPENDENCY_OF`、`TEST_DEPENDENCY_OF` だけでつながる部品です。
- SBOM に印が無いとき（Frappe の SBOM など）は、BOMの行（SG BOM Entry）の一覧で行を選び、「アクション」の「開発用にする」（Mark as Development Only）を押します。外すときは「開発用を外す」（Unmark Development Only）です。
- 照合結果の「開発用だけ」（Development Only）は、その部品の版を含むすべてのリリースで開発用のときに付きます。一覧の絞り込みにも使えます。
- ホームの「未対応の照合結果」は、開発用だけの照合を数えません。「未対応の照合結果（開発用）」に分けて数えます。
- 脆弱性の影響では、開発用の部品を「開発用の部品」（Development-Only Components）の列に分けます。開発用の部品しか無いリリースには「開発用だけ」が付き、ほかのリリースの後に並びます。

## 6. 判定を記録する

| 判定 | 記録する場所 | 影響の調査での扱い |
| --- | --- | --- |
| 照合が間違っている | 照合結果の一覧で行を選び、「アクション」の「誤検知にする」（Mark as False Positive） | 出なくなる |
| 影響がない、修正済み | 影響評価（Impact Assessment）を作り、VEX の状況を選ぶ | チェックを入れたときだけ出る |
| 影響がある、調査中 | 同上 | 出る |

VEX の状況が「影響なし」（Not Affected）のときは、根拠（Justification）に理由を選びます。値は VEX の標準の識別子です。

影響評価を提出すると、照合結果の「判定で対応済み」（Handled by Assessment）が更新されます。

- その部品の版を含むすべてのリリースに、「影響なし」か「修正済み」（Fixed）の影響評価が提出されると付きます。同じ部品の版が、まだ判定していないリリースにも入っていれば付きません。
- 1つのリリースに影響評価が複数あるときは、最後に提出したものを見ます。影響評価を取り消すと外れます。
- 「影響あり」（Affected）と「調査中」（Under Investigation）では付きません。
- ホームの「未対応の照合結果」は、判定で対応済みの照合を数えません。照合結果の一覧では「判定で対応済み」と表示し、絞り込みにも使えます。
- 照合結果の状況（Match Status）は変わりません。照合が正しいかどうか（確認済み、誤検知）は、これまでどおり照合結果で記録します。

## 困ったとき

| 症状 | 確かめること |
| --- | --- |
| 取り込んでも一覧に増えない | worker と socketio が動いているか |
| 文書を保存すると更新の衝突のエラーが出る | 検証の途中で開いた可能性がある。画面を再読み込みする |
| 影響の調査に出ない | 文書を受け入れたか、対象リリースを選んだか、部品に PURL があるか、版が範囲（`IMP-VERSION-RANGE`）になっていないか |
| 台数が0になる | 実機の搭載リリース（Installed Releases）にそのリリースがあるか |
| 実機の登録でエラーになる | シリアル番号が製品カテゴリの形式に合っているか |
