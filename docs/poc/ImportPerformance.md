# SBOM の取込の性能

2026年11月6日に、取込と照合の性能を確かめるために計測した結果です。公開 SBOM と実際の OSV API でも確かめました。

## 結論

| KPI | 結果 |
| --- | --- |
| 1,000部品で5秒以内（OSV の通信を除く） | CycloneDX 2.5〜3.7秒、SPDX 3.2〜4.3秒で満たす |
| CycloneDX の2万部品で3分以内 | 50秒で満たす |
| SPDX の2万部品 | 406秒（課題として残っている） |

当初の目標「1,000部品で2秒以内」は、どの条件でも満たしませんでした。取込はバックグラウンドのジョブで動き、利用者は結果を待たないので、目標を5秒に変えました。

## 最初の計測の誤り

最初の計測の合成データには `externalReferences` の URL がありませんでした。実 SBOM（juice-shop、CycloneDX 1.4、1,115部品、URL 4,450件）をワーカーで取り込むと92.4秒かかり、KPI を満たしていませんでした。

原因は `iri-reference` の書式チェックです。jsonschema が使う汎用パーサーは1件あたり約20ms かかります。これを軽いチェック（`syntax.is_iri_reference`）に置き換えました。実データの URL 4,296種類で、判定は元のパーサーと一致しました。

| 条件 | 元のパーサー | 軽いチェック |
| --- | ---: | ---: |
| URL 4,296種類の判定 | 90.0秒 | 0.014秒 |
| 実 SBOM の取込と検証（ワーカー） | 92.4秒 | 4.16秒 |

元のパーサーは `http://[::1]:8080/a` を拒否しますが、RFC 3987 では正しいので受け入れます。

## データと環境

- 開発用コンテナ（frappe_docker）、Python 3.14.8、Frappe 16.55.1、MariaDB 11.8.9、cyclonedx-python-lib 11.12.0、spdx-tools 0.8.5
- MariaDB のバッファは既定の128MB。計測用のプロセスを直接実行し、同じマシンで別のコンテナが動いている状態
- 合成データ。全部品に PURL、供給者、ライセンス、SHA-256 があり、依存関係は部品数と同じくらいの一直線。CycloneDX は1部品に URL が4件（実 SBOM と同じくらい）
- SBOM ごとに脆弱性50件を作り、50件の照合結果を作る
- 検証エラーは全件0件

順に `import_file`、`validate_bom`、`create_exact_matches`、`create_range_matches`、`rebuild_release` を呼び、それぞれ commit までの時間を測りました。OSV の通信と、提出（Submit）の処理は含みません。OSV の問い合わせは1,000件あたり1.8秒です（T-01）。

## 1,000部品（中央値）

「照合と索引」は `create_exact_matches`、`create_range_matches`、`rebuild_release` の合計です。SPDX は URL の書式チェックを通らないので、最初の計測の値です。

| 条件 | 形式 | 取込 | 検証 | 照合と索引 | 合計 |
| --- | --- | ---: | ---: | ---: | ---: |
| 毎回新しいプロセス（3回） | CycloneDX | 1.44秒 | 2.05秒 | 0.20秒 | 3.71秒 |
| 毎回新しいプロセス（3回） | SPDX | 1.83秒 | 2.24秒 | 0.20秒 | 4.26秒 |
| 同じプロセスで連続（5回） | CycloneDX | 1.44秒 | 0.84秒 | 0.19秒 | 2.52秒 |
| 同じプロセスで連続（5回） | SPDX | 1.83秒 | 1.13秒 | 0.20秒 | 3.16秒 |
| カタログ約3万件の後（5回） | CycloneDX | 1.59秒 | 0.92秒 | 0.20秒 | 2.72秒 |
| カタログ約7万件の後（5回） | SPDX | 2.00秒 | 1.03秒 | 0.19秒 | 3.24秒 |

連続の行は、各形式の最初の1回を除いています。実 SBOM をワーカーで取り込んだ時間（1,115部品で4.16秒）は、毎回新しいプロセスの行に近い値です。

## 2万部品（各1回）

| 形式 | 取込 | 検証 | 合計 |
| --- | ---: | ---: | ---: |
| CycloneDX | 29秒 | 19秒 | 50秒 |
| SPDX | 36秒 | 368秒 | 406秒 |

SPDX の検証は `check_spdx` だけを測っても、PURL やハッシュなどの項目を外したファイルで343秒、項目ありで374秒でした。項目の量は主な原因ではありません。

## ライブラリ選定のときの計測との違い

ライブラリ選定のときの SPDX の検証は1,000部品で0.47秒、2万部品・関係2万件で155.6秒でした。今回は2倍以上かかっています。原因は調べていません。別のコンテナが動いていたことによる環境の差かもしれません。

## 取込を速くするなら

1,000部品の SPDX を cProfile で測ると3.96秒（計測の負荷を含む）で、次の処理が目立ちました。

| 処理 | 時間 | 呼び出し |
| --- | ---: | ---: |
| 採番（`getseries`） | 1.05秒 | 2,001回 |
| 名寄せの重複検出（`mark_duplicates`） | 0.45秒 | 1回 |
| ライセンスの存在確認（`exists`） | 0.43秒 | 1,001回 |
